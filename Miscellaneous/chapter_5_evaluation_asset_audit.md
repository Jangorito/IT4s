# D. Gaps and Missing Evidence

## D1. Missing Evidence

- No drummer/user/listener study. The codebase cannot prove perceived responsiveness, collaborative feel, creativity, or musical quality.
- No measured end-to-end latency from physical hit detection through Unity processing to ChucK playback.
- No hardware validation dataset comparing true acoustic onset time with Bela-reported sample timestamps.
- No long-running session logs showing stability across many repeated turns.
- No active tests for `FeatureTransformer`, even though it produces the current audible AI response.
- No active tests for `PatternCompiler`, despite central claims around quantisation and `offsetSamples`.
- No PlayMode or audio-engine integration tests verifying ChucK playback timing in a running Unity scene.
- No clean per-session export format for live/runtime runs. The debug UI is rich, but evidence capture appears mostly manual/screenshots/logs.
- No objective comparison between audible interim `PatternTurn` output and planned `ResponsePlan` / `SkeletonPattern` intent.
- No evidence that tempo adaptation, long-term memory, performer modelling, or microtiming-aware planning are implemented.

## D2. Weakly Supported Claims

- "The final AI response is musically distinctive": weak for audible output. Strong only for skeleton-level structural distinctiveness.
- "The system is real-time responsive in performance": moderate. Architecture supports reactivity, but no measured latency or user-perceived responsiveness evidence.
- "Closed-loop interaction is musically coherent": moderate. State closure is tested, but musical coherence needs listening/user evidence.
- "Microtiming is expressive in planning": weak. `offsetSamples` are preserved and played back, but most analysis/planning ignores them.
- "The response-generation layer realises planner intent": weak. The code explicitly shows the opposite: planner/skeleton exist, but audible output is still interim transformation.

## D3. Easy Additions That Would Strengthen Chapter 5

- Add a small runtime session exporter subscribing to `TurnLoopController` events and writing one JSON/Markdown trace per turn: phase timestamps, `TurnWindow`, compiled `PatternTurn`, analysis summary, `ResponsePlan`, skeleton summary, and generated audible pattern.
- Add `PatternCompilerTests` for step quantisation, offset calculation, collision max-velocity behaviour, and boundary hits.
- Add `FeatureTransformerTests` for `Auto`, `EchoAccent`, `EndFill`, and `SparseOrnament`, including density/gap scenarios. This would make the current audible layer evaluable instead of merely described.
- Add a "planned vs audible" diagnostic row to the batch runner: compare `ResponsePlan.TargetDensity` and skeleton selected count with the final `FeatureTransformer` output density and overlap/gap fill.
- Add a compact case-study report generator that selects 3-5 representative synthetic cases and writes a readable Markdown trace from analysis -> planner scores -> skeleton metrics.
- Add simple stopwatch/timestamp debug logs around capture completion, analysis/planning/skeleton/generation duration, and playback trigger. Even rough timing proxies would strengthen reactivity claims.
- Add a small README beside `DiagnosticsOutput/TurnAnalysisResponsePlanner` documenting exactly how the outputs were generated and which version should be treated as current.
