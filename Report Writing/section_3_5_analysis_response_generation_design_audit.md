# Section 3.5 Design Audit - Analysis and Response Generation

## Bottom-Line Verdict

- The live Unity turn loop does execute `TurnAnalyser -> ResponsePlanner -> SkeletonBuilder`.
- The live audible response is **not** generated from the `ResponsePlan` or `SkeletonPattern`.
- The played AI pattern is currently generated by a separate, simpler heuristic path: `FeatureTransformer.Transform(compiledPattern)`.
- The exact divergence occurs inside `AiResponsePreparationFlow.Prepare`, after plan/skeleton creation and before playback.

Scope note:

- "Affects audible output" below means "changes the played rhythmic content", not merely "must exist for the controller to avoid erroring".
- In the live controller, analysis/planning/skeleton services are required dependencies, but their current outputs do not determine the played `PatternTurn`.

## 6. Divergence Point

### Exact divergence

The divergence occurs inside `AiResponsePreparationFlow.Prepare`.

Sequence:

1. `TurnAnalyser.Analyze(compiledPattern)` produces `TurnAnalysisResult`: `AiResponsePreparationFlow.cs:67-72`.
2. `responsePlanner.Plan(analysis)` produces `ResponsePlan`: `AiResponsePreparationFlow.cs:80-85`.
3. `skeletonBuilder.BuildSkeleton(CreateSkeletonBuildRequest(compiledPattern, analysis, responsePlan))` produces `SkeletonPattern`: `AiResponsePreparationFlow.cs:87-101`.
4. The code then **does not transform the skeleton into a playable pattern**.
5. Instead, it calls `featureTransformer.Transform(compiledPattern)`: `AiResponsePreparationFlow.cs:110-115`.

The class comment makes this explicit:

- "ResponsePlan is intentionally produced and exposed first, but generation still transforms the compiled human pattern directly. That gap remains explicit for now.": `AiResponsePreparationFlow.cs:110-111`.

The live controller then reinforces the split:

- It stores the skeleton through `StoreSkeletonDebugSnapshot(...)`: `TurnLoopController.cs:901-910`, `1045-1057`.
- It plays `LastGeneratedAiPatternTurn` through `aiTurnPlayer.PlayTurn(...)`: `TurnLoopController.cs:936-937`.

The playback interface also reinforces the split:

- `IT4ChuckTurnPlayer.PlayTurn(...)` accepts only `PatternTurn`: `IT4ChuckTurnPlayer.cs:80-160`.
- The ChucK script knows only `velocity[]`, `offsetSamples[]`, tempo, and metronome flags: `IT4_TurnPlayer.ck:10-17`, `100-162`.

Plain technical explanation:

- The reasoning branch and the audible branch currently coexist in the same preparation phase, but they do not join back together.
- Analysis, planning, and skeleton generation run.
- The final played pattern is then created separately from the compiled human pattern by `FeatureTransformer`.
- Therefore the planner/skeleton outputs are currently **observed**, **stored**, and **evaluated**, but not **realised as sound**.

Test evidence that this is intentional/current behaviour:

- With no skeleton builder, generated output equals `new FeatureTransformer().Transform(compiledPattern)`: `AiResponsePreparationFlowTests.cs:20-59`.
- Even when a skeleton builder is present and runs first, generated output still equals `new FeatureTransformer().Transform(compiledPattern)`: `AiResponsePreparationFlowTests.cs:62-100`.
- Analysis and planning still happen before failure if `FeatureTransformer` is missing, showing the reasoning branch is separate from the final content generator: `AiResponsePreparationFlowTests.cs:130-162`.

## 8. Section 3.5 Design Guidance

### Recommended title

- **Preferred:** `3.5 Structural Response Generation and Current Output Coupling`

Reason:

- `3.4` already covers interpretable analysis and planning.
- `3.5` should focus on how plans are intended to be turned into structure.
- The title should also leave room to acknowledge that the live output path is not yet fully coupled to that structure.

### What Section 3.5 should include

- The response categories as structural intents: `Mirror`, `Complement`, `Simplify`, `Intensify`, `Contrast`, `Fill`.
- The core plan fields: `ResponseType`, `TargetDensity`, `ComplementarityBias`, `PreserveAnchors`, `MirrorEnding`, `TurnLengthSteps`.
- The structural-generation design:
  - `ResponsePlan -> ResponseBehaviourProfile`
  - `ResponseBehaviourProfile + SourceTurn + SourceAnalysis -> SkeletonPattern`
- The fact that skeleton generation is a real implemented subsystem, not just a placeholder.
- A short, explicit implementation-boundary note: the live audible path currently uses `FeatureTransformer` rather than a skeleton-to-sound realisation stage.

### What Section 3.5 should avoid claiming

- That the audible response is generated from `SkeletonPattern`.
- That `ResponseType` selections are currently realised faithfully in sound.
- That plan parameters such as target density, complementarity, anchor preservation, or mirrored endings are directly enforced in playback.
- That the current system already delivers a complete analysis-to-planned-structure-to-sound pipeline.
- That current musical output quality should be taken as evidence that the planner/skeleton architecture is fully realised.

### Where the skeleton/output divergence should be mentioned

- **Chapter 3:** Yes, briefly.
- **Chapter 4:** Yes, explicitly.

Recommended split:

- **Chapter 3:** one concise design-boundary statement is enough.
  - Say that the system implements analysis, planning, and structural skeleton generation as the intended reasoning architecture.
  - Say that the present live playback path remains coupled to an interim heuristic transformer rather than the structural skeleton.
- **Chapter 4:** give the full implementation/evaluation treatment.
  - exact code divergence
  - what is live vs diagnostic
  - plan/skeleton vs output mismatch
  - consequences for claim scope and evaluation interpretation

### How much detail should be reserved for Chapter 4

- **Chapter 3:** high-level architecture plus one explicit caveat.
- **Chapter 4:** the detailed evidence.

Keep in Chapter 4:

- the exact `AiResponsePreparationFlow` divergence
- the `FeatureTransformer` heuristic logic
- the `PatternTurn -> ChucK` payload path
- the fact that diagnostics/evaluation runners exercise planner/skeleton outputs separately from live playback
- any quantitative or behavioural analysis of plan-vs-output mismatch

Keep Chapter 3 focused on:

- intended structural reasoning design
- current integration boundary
- safe claims only

## Safe one-sentence framing

If Section 3.5 needs a single safe technical framing sentence, the safest version is:

- The system implements a live analysis, planning, and structural skeleton-generation architecture, but current audible playback is still produced by a separate heuristic `FeatureTransformer` path rather than by direct realisation of the planned skeleton.
