# Section 3.1 Design Principles and System Framing - Evidence Handoff

Purpose: this file collects implementation evidence, recoverable rationale, limitations, negative evidence, local-literature pointers, and claim candidates for drafting dissertation Section 3.1, "Design Principles and System Framing".

This is not polished dissertation prose. It is an evidence pack for later academic writing.

Core framing question:

> Given the theoretical landscape and the implemented system, what kind of system SHOULD Intelli-Trading Fours be understood as?

Recommended framing:

> Intelli-Trading Fours is best framed as a closed-loop, turn-based, human-AI rhythmic interaction architecture with interpretable symbolic analysis and planning, plus an interim/prototype response-realisation layer. It should not be framed as a finished autonomous AI drummer, an offline generative model, or an end-to-end raw-audio system.

## B. Recoverable Design Rationale

| Rationale | Evidence | Why The Inference Is Justified | Status |
|---|---|---|---|
| 1. Real-time bounded responsiveness is a primary design principle. | Bela sample timestamps in `render.cpp`; sample-clock reconstruction in `OscHitReceiver`; bounded capture in `HumanTurnCaptureFlow`; fixed phrase duration in `MusicalTimingConfig`; ChucK sample scheduling in `IT4_TurnPlayer.ck`; planner docs requiring near-instant response. | The architecture repeatedly avoids open-ended computation: capture has a known end, analysis modules are deterministic, planning is compact, and playback is scheduled from symbolic arrays. | explicit in docs; implicit in timing architecture |
| 2. Turn segmentation simplifies interaction into analysable musical objects. | `TurnPhase`; `TurnWindow`; `PatternCompiler`; `TurnLoopController` only starts capture from `WaitingForHuman`; dissertation spec frames trading fours as the interaction model. | The system treats each human contribution as a bounded object that can be captured, compiled, analysed, answered, and archived. This makes live interaction tractable. | explicit in docs; implicit in data flow |
| 3. Interpretable planning is preferred over opaque generation. | `ResponsePlanner`, `ResponsePlan`, `ResponsePlannerDebugSnapshot`, `ResponsePlanner_Spec.md`; response types and plan fields are named musical controls. | The planner outputs human-readable intent before generation. The docs explicitly say the planner is not a generator and should remain lightweight and debug-friendly. | explicit in docs/comments; implicit in interfaces |
| 4. Symbolic rhythm-first reasoning is a core design choice. | `HitEvent -> TurnWindow -> PatternTurn -> TurnAnalysisResult -> ResponsePlan`; `PatternTurn` velocity/offset arrays; Turn Analysis docs state analysis operates on quantised step-grid representation. | The main reasoning layers do not consume raw audio. They consume a structured rhythmic representation, preserving enough timing information for playback while enabling feature extraction. | explicit in docs; implicit in representation boundaries |
| 5. Listening, analysis, planning, generation, and playback are deliberately modular. | `TurnLoopController` injection points; `AiResponsePreparationFlow`; `IResponsePlanner`; `ISkeletonBuilder`; `IT4ChuckTurnPlayer`; debug presenters separate UI from orchestration. | Responsibility boundaries are repeatedly expressed as classes, interfaces, data objects, and callbacks. This supports testability and replacement of incomplete modules. | implicit in architecture; explicit in spec |
| 6. IT4s is interaction architecture before it is standalone generation architecture. | `TurnLoopController` cycle; opt-in return to `WaitingForHuman`; dissertation spec says strongest contribution is not a finished AI drummer but the real-time turn-taking architecture. | The implemented loop is triggered by human input and re-arms for repeated exchange. Generation is subordinate to the interaction cycle. | explicit in dissertation spec |
| 7. Debugability and observability are design values. | `OnPhaseChanged`, `OnHumanPatternCompiled`, `OnHumanTurnAnalysed`, `OnResponsePlanned`, `OnSkeletonGenerated`; debug renderers; debug snapshots; skeleton metadata and reason flags. | The system exposes almost every major intermediate state. This is excessive for mere runtime operation but valuable for research, tuning, and dissertation evaluation. | explicit in comments/specs; implicit in tooling |
| 8. The prototype chooses controllable interim mechanisms over premature end-to-end ML. | `FeatureTransformer` rule modes; `ResponsePlanner` weighted/rule-guided logic; `SkeletonBuilder` score-and-select scaffold; docs defer learned tuning, motif transformation, richer generation, and long-term memory. | The code prioritises explainable working interaction over more ambitious learned response generation. This makes the prototype defensible but limited. | explicit in docs; implicit in absence of ML loop |
| 9. Timing responsibility is distributed intentionally across subsystems. | Bela owns hit sample time; Unity owns orchestration and symbolic scheduling; ChucK owns sample-level playback timing; loop closure currently estimated in Unity. | The architecture uses the right timing domain for each stage, but the lack of ChucK completion callback is a known limitation. | implicit in integration boundaries; explicit in dissertation spec |
| 10. Musical dialogue is framed as structured response, not unrestricted improvisation. | Trading-fours loop, response types, complementarity/mirroring parameters, anchor preservation, ending mirroring, skeleton source-relation maps. | The system does not simply generate "some rhythm." It generates or intends to generate a response whose relationship to the human turn is named and inspectable. | implicit in naming/data flow; explicit in docs |

## C. Trade-offs and Limitations

| Trade-off / Limitation | Evidence | Current Choice |
|---|---|---|
| Interpretability vs expressive richness | `ResponsePlanner` uses explicit response types and bounded plan parameters; `TurnAnalysis` uses density/energy/anchor/end/SAP features; `FeatureTransformer` uses simple rule modes. | Deliberate. The system favours explainable response logic over high-dimensional expressive generation. |
| Structural clarity vs improvisational fluidity | `TurnPhase` separates human capture, compilation, response generation, and playback; capture only begins from `WaitingForHuman`. | Deliberate. Turn segmentation makes interaction tractable but reduces continuous mutual adaptation. |
| Deterministic control vs stochastic surprise | `ResponsePlannerTests` assert deterministic plans; skeleton spec says zero jitter should be deterministic; `SkeletonPatternSummary` exposes whether stochastic tie-breaks were used. | Deliberate for v1, with future bounded stochasticity left open. |
| Symbolic tractability vs low-level nuance | Bela detects hits and velocities; `PatternCompiler` quantises to grid velocity/offset arrays; analysis operates on `PatternTurn`. | Deliberate and partly necessary. Microtiming offsets are preserved, but raw audio nuance and timbre are mostly discarded. |
| Bounded turn windows vs continuous co-improvisation | `HumanTurnCaptureFlow` computes fixed end sample from BPM/bars; AI response playback is a separate phase. | Deliberate. It supports trading-fours exchange but cannot model simultaneous interactive push-pull. |
| Prototype controllability vs autonomous sophistication | Dissertation spec and `AiResponsePreparationFlow` state that final response realisation is incomplete; current audible output still uses `FeatureTransformer`. | Provisional. This should be openly framed as an interim response layer. |
| Modular architecture vs end-to-end optimisation | Separate data objects and modules: `HitEvent`, `TurnWindow`, `PatternTurn`, `TurnAnalysisResult`, `ResponsePlan`, `SkeletonPattern`, ChucK bridge. | Deliberate. It improves testing and reasoning but prevents joint optimisation across the whole pipeline. |
| Sample-accurate local timing vs global completion certainty | Bela and ChucK use sample-time concepts; Unity loop closure estimates AI playback completion from `PatternTurn` duration rather than receiving a ChucK callback. | By necessity/provisional. Timing is strong locally but not fully closed at the integration boundary. |
| Fixed tempo/grid simplicity vs tempo-following flexibility | `MusicalTimingConfig` centralises BPM and steps per quarter; `PatternCompiler` assumes fixed-BPM quantisation. | Deliberate/provisional. It keeps the prototype stable but does not infer tempo from performer timing. |
| Single-pad rhythmic focus vs richer drumset dialogue | Bela code uses a single piezo channel/pad path; `PatternTurn` stores one velocity array rather than multi-instrument voices. | By necessity/prototype scope. It narrows the musical domain to make turn interaction feasible. |
| Turn-local response vs long-term musical memory | Dissertation spec lists long-term memory/history as future work; planner operates on current `TurnAnalysisResult`. | Provisional. The current system supports local exchange, not evolving multi-turn narrative. |
| Lightweight analysis vs deeper motif understanding | Turn Analysis docs defer repetition/motif analysis because of short turns, single-pad input, ambiguity, and complexity. | Deliberate for v1. This supports responsiveness but weakens claims about deep musical understanding. |

## D. Negative Evidence (What is NOT implemented)

| Absence | Supporting Evidence | Framing Consequence |
|---|---|---|
| No fully learned end-to-end response generator in the live loop. | Live path uses `TurnAnalyser`, `ResponsePlanner`, optional `SkeletonBuilder`, and `FeatureTransformer`; docs describe learned tuning/richer generation as future work. | IT4s should be framed as interpretable reactive/planning architecture, not an end-to-end neural drummer. |
| No raw-audio semantic analysis front-end. | Bela front end performs threshold/peak/refractory hit detection and sends `/it4/hit`; Unity receives discrete `HitEvent`s; analysis consumes `PatternTurn`. | The system is rhythm-event-first and symbolic, not raw-audio-to-music reasoning. |
| No continuous co-improvisation without turns. | `TurnLoopController` gates capture through `WaitingForHuman`, `CapturingHuman`, `GeneratingAiResponse`, and `PlayingAiResponse`; hits trigger capture only in the waiting phase. | The central interaction identity is alternating dialogue/trading fours, not simultaneous improvisational co-performance. |
| No opaque latent-only planner. | `ResponsePlan` fields and planner debug snapshots expose response type, density, complementarity, anchor preservation, ending choice, and scores. | The planner is dissertation-legible and controllable rather than black-box. |
| No direct audio-to-audio accompaniment. | Output path sends symbolic velocity/offset arrays to ChucK, which schedules playback events. | IT4s should not be described as audio generation or audio continuation. It is symbolic response rendered to sound. |
| No finished autonomous long-form composition engine. | Dissertation spec states no deep long-term memory; current planning is turn-local; future work includes richer history/memory. | The system is a local interaction loop, not an autonomous composer. |
| No completed planner-driven full response realiser. | `AiResponsePreparationFlow` explicitly exposes `ResponsePlan` but current generation still transforms the compiled human pattern directly; skeleton builder outputs scaffold only. | The response-generation layer must be described as partial/interim. |
| No ChucK playback-complete callback. | `ConfigureReturnToWaitingAfterAiPlayback` and dissertation spec state loop closure currently estimates duration from `PatternTurn`. | Closed-loop architecture is implemented, but playback feedback is not fully event-confirmed. |
| No robust repetition/motif model in v1 analysis. | Turn Analysis docs defer repetition because short single-pad turns make it ambiguous and costly. | The system analyses surface rhythmic features, not deep motivic development. |
| No unconstrained poly-instrument dialogue model. | Current capture path and `PatternTurn` representation are effectively single-stream velocity/offset data. | The research contribution is rhythmic turn exchange, not full ensemble-level drum intelligence. |
| No heavy search/candidate-evaluation response planner. | ResponsePlanner docs explicitly reject becoming a generator or hidden evaluator; skeleton docs reject heavy search and opaque end-to-end generation. | The design privileges fast, bounded, inspectable decisions over global optimisation. |
| No final motif/ending/constraint-pass chain after skeleton. | Skeleton docs describe intended pipeline `ResponsePlan -> SkeletonBuilder -> MotifTransformer -> EndingAdjuster -> ConstraintPass -> PatternTurn`, but implemented live response still uses interim transformation. | Skeleton generation is a forward path, not yet the complete realised architecture. |
